# 설계 v5: B2B 온보딩, 1·2·3차 스케줄, 쾌적 의견, 두 에이전트 협의 (2026-11-20)

## 목표

문제: 학교·쇼핑몰처럼 일정이 자주 바뀌는 건물은 고정 스케줄로 효율적인 냉난방이 어렵습니다.
v5는 부산대 IT관 시연을 그대로 두고, 같은 엔진을 **어느 건물이든 연결해서 쓰는 B2B 서비스** 흐름으로 감쌉니다.

- 비용은 최소로, 재실자 쾌적은 유지하는 운전 계획을 만들고, **자동 운전** 하거나 **추천만** 합니다.
- 계획은 세 번(1차 월간 → 2차 주간 → 3차 일일) 만들고, 매번 새로 들어온 데이터와 맞는지 **정합성 점검**을 돌립니다.
- 비용과 쾌적은 서로 맞바꾸는 관계라서, **관리자 에이전트 '북항이'**와 **사용자 에이전트**가 시뮬레이터 결과를 놓고 협의합니다.

## 중앙 제어기 연결 (현실적인 경로)

캠퍼스 건물의 중앙제어 PC는 시설 전용 폐쇄망에 있어서 클라우드가 직접 접속할 수 없습니다. 그래서 **현장 게이트웨이**를 같은 망에 설치하고, 게이트웨이가 중앙제어기와 BACnet/IP(47808)·Modbus TCP(502)·제조사 API(HTTPS)·OPC UA(4840)로 통신한 뒤 클라우드로는 아웃바운드 TLS로만 연결하는 구성을 기본으로 둡니다. VPN·허용 IP 직접 연결과 운전 이력 파일 업로드도 고를 수 있습니다.

- 온보딩은 관리자에게 중앙제어 PC 주소(IP:포트)와 프로토콜을 받고, 게이트웨이 연결 코드와 설치 명령을 보여 줍니다.
- 연결 테스트는 게이트웨이 확인 → 중앙제어기 응답 → 포인트 탐색 → 강의실 자동 매핑 → 현재값 읽기 → 쓰기 권한 확인(시험 모드) 순서로 진행합니다.
- **데모에서는 이 핸드셰이크를 시뮬레이션하고, IT관 열모델 시뮬레이터가 중앙제어기 역할을 합니다.** 화면에 그렇게 표시합니다.
- 조정안이 적용되면 게이트웨이를 거쳐 실내기 설정온도(`AV:IDU-306-1/HeatSetpoint`)와 환기 단계(`MV:ERV-306/FanLevel`) 쓰기 명령을 보내고 기록합니다(데모: 즉시 응답).

## 1·2·3차 스케줄과 정합성 점검 (`backend/app/planning.py`)

| 차수 | 기간 | 쓰는 데이터 | 점검 | 조정안 |
|---|---|---|---|---|
| 1차 | 월 | 시간표, 학사일정·공휴일, 실측·예보·평년 기후, 설비, 요금, 정책 | 시간표 반영, 공휴일, 정원 대비 인원, 실외기 동시 기동, 정책 온도, 예보 기반 예열(11), CO₂ 환기 계획(13), 월 예상 요금 | 없음(기본 계획) |
| 2차 | 주(월~일) | 행사·예약, 주간 예보, 최근 7일 의견, 재실 밀도, CO₂ | 행사 반영, 예보와 지난주 비교(11·15), 의견 패턴, 재실 추세, CO₂ 환기(13), 일사·방향(12), 잔열·잔냉(14) | 의견이 반복된 강의실 설정온도(상위 3곳), 환기 단계 |
| 3차 | 일 | 초단기실황, 실내 온도 센서, CO₂ 센서, 재실 밀도, 오늘 일정, 어제·오늘 의견 | 날씨 급변(15, 편차가 기준 이상이면 예보 대신 실황으로 다시 계획해 예열 변화를 보여 줌), 예열(11), 일정 정합, 실내 센서, CO₂(13), 재실 감지, 잔열(14), 일사(12), 쾌적 의견 | 오늘 의견이 들어온 강의실 설정온도, 강 단계 환기 |

- 기준일: 3차와 2차는 오늘 수업이 없으면 **다음 운영일**을 검증합니다(주말에는 월요일 계획).
- 설정온도 조정은 정책 범위 안에서 0.5℃ 단위로만 움직입니다. 효과는 같은 날씨·같은 재실로 **AI 운전을 다시 시뮬레이션**한 차이입니다.
- '답답함' 태그가 붙은 의견은 온도가 아니라 공기질 신호라서 설정온도 통계에서 빼고 환기 근거로 씁니다.
- 매시 20분 스케줄러가 날씨를 갱신한 뒤 3차(오늘)와 2차(이번 주)를 다시 검증합니다. 자동 운전이면 새 조정안이 바로 적용됩니다.

## 운전 모드와 조정안

- **자동 운전**: 새 조정안은 바로 `applied`가 되고 제어 명령이 기록됩니다. 추천 모드에서 자동으로 바꾸면 대기 중인 조정안을 적용합니다. 다만 의견 3건 미만으로 만든 조정이나 한 번에 0.5℃를 넘는 변경은 자동 운전에서도 승인을 기다립니다(현장 연구는 사람이 설정을 적용한 수준까지가 근거라서, Sawada 2025).
- **추천 모드**: 조정안은 `pending`으로 남고, 상단 막대의 "승인 대기" 또는 AI 스케줄링 화면에서 승인·거절합니다.
- 적용된 설정온도 조정은 `service.day_settings()`로 그날의 AI 운전 설정(`room_sp`)에 들어가서, 운전 현황·타임라인·절감 효과에 그대로 반영됩니다. 고정·수동·규칙 비교 운전은 바뀌지 않습니다. 조정이 없으면 계산 결과와 기존 수치는 바뀌지 않습니다.

## 두 에이전트 협의 (`backend/app/agents.py`)

한쪽이 제안하고 다른 쪽이 반박하며, 매 제안을 시뮬레이터가 검증하는 **제안–검증 루프**입니다. 처음에는 GAN의 생성자·판별자에 비유했지만, 문헌상으로는 LLM을 외부 검증기와 묶는 LLM-Modulo(Kambhampati 2024)가 정확한 이름이라 그렇게 부릅니다. 평가 결과는 [evaluation_agents.md](evaluation_agents.md)에 있습니다.

1. **자료 묶음(dossier)**: 정책 범위, 요금, 예보, 강의실별 설정온도 후보(정책 범위 0.5℃ 간격)마다 시뮬레이터로 계산한 전력·수업 중 PMV, 최근 7일 의견, 예상 인원, 예상 CO₂.
2. **북항이(관리자 에이전트)**가 제안 → 시뮬레이터 검증 → **사용자 에이전트**가 반박·수정 → 검증 → 2라운드까지.
3. 각 발언은 구조화 출력(입장, 메시지, 확인한 근거 trace = 어떤 자료에서 무엇을 확인했는지, 강의실별 제안, 수용 여부)입니다. 메시지의 수치는 자료와 시뮬레이터 값에서만 인용하고, 평가 스크립트가 직접 인용률을 잽니다(96~97%).
4. **판정**: 합의하면 그 안을, 아니면 두 제안 사이에서 강의실마다 `전기요금 + 쾌적 벌점`이 가장 작은 설정온도를 고릅니다. 쾌적 벌점은 현재 계획 대비 PMV 악화(의견이 반복된 강의실은 목표를 0.3 높이고 가중치 3배)이고, 가중치는 정책 값 `comfort_won`(기본 600원/PMV·실·일)입니다. 비교를 위해 같은 함수로 정책 범위 전체에서 고른 최적안도 함께 계산해 보여 줍니다.
5. 결과는 같은 설정온도로 바뀌는 강의실끼리 묶어 조정안으로 만들고, 같은 강의실의 기존 대기 조정안은 "에이전트 협의안으로 대체"로 닫습니다.

- 모델: Bedrock Claude Haiku 5.5(`MODEL_AGENTS`로 변경 가능), effort low, JSON 스키마 출력. 4턴에 약 30~40초입니다. 화면은 턴이 끝날 때마다 받아서 그립니다.
- Bedrock이 실패하면 같은 흐름을 규칙 기반 에이전트로 이어 가고 화면에 표시합니다(`ai: false`).

## 시뮬레이션 랩 (`/lab`, `backend/app/lab.py`)

운영 화면과 분리된 별도 페이지입니다. 날마다 두 에이전트가 설정온도를 협의하고(규칙 기반 또는 Bedrock LLM), 그 결과로 하루 운전을 다시 시뮬레이션해서 네 가지 운전과 비교합니다.

| 비교 대상 | 내용 |
|---|---|
| 현재 운영 | 현장 인터뷰를 재현: 08:30~22:30 고정 운전, 난방 22℃(냉방 26℃ 가정) |
| 시간표 연동 규칙 | 시작 10분 전 On, 종료 5분 전 Off, 15분 이내 공백 유지 |
| AI 예측 제어 | 에이전트 없이 기본 설정온도 |
| AI + 에이전트 협의 | 그날 합의한 강의실별 설정온도 |
| 실측 | 운영자가 올린 냉난방 계량값(시간·일 단위 CSV) |

- 지표: 전력량, 요금, 최대 전력, 평균 PMV, PMV ±0.5 안 비율, 쾌적 범위 이탈(K·분), 시작 이탈, 의견이 반복된 강의실의 PMV, 합의율, 정책 준수율, LLM 호출 수, 계산 시간.
- 실측을 올리면 먼저 "현재 운영" 시뮬레이션이 실측을 재현하는지 ASHRAE Guideline 14(시간 단위 NMBE ±10%, CV(RMSE) 30%; 월 단위 ±5%, 15%)로 확인합니다. 통과해야 에이전트 운전의 절감을 실측 대비로 읽을 수 있습니다.
- 격리 실행이라 조정안·제어 명령을 만들지 않고, 적용된 조정도 무시해서 모든 운전이 같은 기본 설정에서 출발합니다.
- 첫 실행 결과(11/16~11/20, 규칙 기반 에이전트): 현재 운영 616 kWh → 에이전트 129 kWh(−79%)이지만 PMV ±0.5 안 비율은 51.5% → 35.0%로 낮아집니다. 에이전트는 AI 단독보다 전력을 5.2% 더 쓰고, 의견이 반복된 강의실의 PMV를 −0.89 → −0.84로 올립니다. 쾌적을 절대 기준까지 올리지는 못한다는 점을 그대로 보여 줍니다.

## 가정과 한계 (화면에도 표시)

- **CO₂ 센서·재실 밀도(Wi-Fi)는 시뮬레이션**입니다. 열 시뮬레이터와 같은 재실(무단 공강·조기 종료 포함)과 계획한 환기 단계로 질량 수지를 1분 간격으로 풀어 계산합니다. 환기 단계(약 600·중 1000·강 1400 m³/h, 99 m² 기준)는 가정값입니다.
- 환기 단계 조정의 에너지 영향은 열모델 밖에서 계산한 추정치입니다(전열교환 60%, COP 3).
- 강의실 방향(남·북·동·서)은 도면이 없어 가정값이며 운영 규칙에서 바꿀 수 있습니다. 일사·방향은 점검과 설명에 쓰고, 열모델의 일사 이득(방향 구분 없음)은 기존 수치를 지키려고 바꾸지 않았습니다.
- 데모 건물에는 의견 기록이 없어서, 최근 14일 AI 운전의 수업별 PMV로 재실자 의견을 만들어 넣었습니다(`source: simulated`, 화면에 "시뮬레이션" 배지). QR과 관리자 입력은 실제로 저장됩니다.
- 11월 말에는 정책 범위(난방 20℃ 안팎)에서도 PMV가 -1 안팎으로 나옵니다. 열모델의 구조체 온도를 평균복사온도로 쓰기 때문입니다. 협의는 절대 기준이 아니라 현재 계획 대비 변화로 판단합니다.
- 로그인·회원가입은 목업이고, 백엔드는 건물 하나(IT관)만 계산합니다. 새 계정의 온보딩도 같은 시뮬레이터에 연결됩니다.
